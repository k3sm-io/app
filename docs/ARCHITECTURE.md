# Architecture

A one-page map of the source. The A-numbers are the binding resolutions of
the k3sm app plan (Amendment A); R-numbers are the earlier resolutions it
keeps; L-numbers are the resolutions of the k3sm lifecycle plan (stop, start
and restart, and the menu).

```
K3smStatus     (library, Foundation only)   reads k3sm, decides visibility
K3smInstall    (library, Foundation only)   the root step as data and text
K3smHost       (library, Foundation, Security) runs the installed CLI after its trust check
K3smMCP        (library, Foundation only)   the read-only MCP server: JSON-RPC, tools, call log
K3smApp        (executable, AppKit/SwiftUI) wires the libraries to the screen and to root
K3smMCPServer  (executable k3sm-mcp)        the MCP server on stdio, inside the bundle
hack/          build, release and gate scripts
```

`K3smInstall` depends on `K3smStatus`; `K3smHost` on both; `K3smMCP` on
`K3smStatus` only, so its tests run against fake reads. `K3smApp` uses
`K3smStatus`, `K3smInstall` and `K3smHost`; `K3smMCPServer` uses `K3smMCP`
and `K3smHost`, so the app and the MCP server read k3sm through one runner
and one trust check. No library imports AppKit, so every decision is
unit-tested without a GUI.

## Help tags

A help tag is the tooltip macOS shows when the pointer rests on a control.
Every one the app shows comes from the catalog, `Help` in
`Sources/K3smStatus/Help.swift`, and follows one standard, after Apple's
guidance for help tags:

- It says what the control does, or what a value means, in one short
  sentence of 12 words or fewer.
- An action starts with its verb ("Delete the pod so its owner recreates
  it"). A value names its unit or its source ("CPU used now, from
  metrics-server, against allocatable").
- A keyboard shortcut follows in parentheses: "Show the details column
  (Command-Option-I)".
- Sentence case, and no closing period unless the tag is two sentences.
- It never repeats the control's visible label, never states the obvious,
  and never carries status or an error, which belong in the view. The two
  kinds of dynamic text a tag may carry are a disabled control's reason and
  the whole of a line the view truncates.

It applies to every button, toggle, picker, menu, stepper, slider and
icon-only control (which also keeps its accessibility label), to every
meter, bar, badge, dot or tile whose label does not say what it means, and
to a column header whose unit is not shown. Plain text and a labelled text
field need none. macOS shows no help tag on a SwiftUI context-menu item or
on an alert's or dialog's buttons, so those carry none; AppKit menu items
do show one, so the app's own menu items set it.

`helpCatalogFollowsTheStandard` checks every entry in the catalog, and
`hack/verify-help.sh` fails the gate on a help string written anywhere else
or on a control with no help tag, unless `hack/help.allow` lists it with a
reason.

`RootScriptBuilder.arguments(for:)` is pinned against `k3sm` `cmd/k3sm/install.go`:

| join | `install --from-staging <dir> --user <user> --agent --server <host> --token-file <dir>/join-token` |
| update a server | `install --from-staging <dir> --user <user>` |
| update a worker | `install --from-staging <dir> --user <user> --agent --server <host>` |
| repair | `install --from-staging <dir>` |
| uninstall | `uninstall` |
| purge | `uninstall --purge --yes --user <user>` |

The lifecycle verbs run the installed CLI, never the app's copy, and take no
lock. `LifecycleScriptBuilder.arguments(for:)` is pinned against `k3sm`
`cmd/k3sm/lifecycle.go` and `main.go`, and the update verbs and the apply's flags against

| verb | argv after `/Library/k3sm/k3sm` |
|---|---|
| stop | `stop --actor user --reason 'from the k3sm app'` |
| start | `start --actor user --reason 'from the k3sm app'` |
| restart | `restart --actor user --reason 'from the k3sm app'` |
| allow connections from other devices | `network lan on` |
| stop allowing them | `network lan off` |
| start the managed update | `update apply --yes [--drain] [--allow-downgrade] [--signature required] --version <tag>` (`UpdateOptions`, `ReleaseTag`) |
| cancel it | `update cancel` |
| abort it | `update abort` |

The Builds tab runs every k3sm verb as the user, never as root: the history's
(`build ls -o json`, `build logs [-f] <id>`, `build cancel <id>`, `build rm <id>`)
read and write the invoking user's ledger, and the engine's (`builder up`,
`builder down`, `builder delete`, `build prune`, `build prune --force`) take
no `--work-dir`, so the CLI picks the user's admin kubeconfig as `k3sm kubectl`
does (k3sm `cmd/k3sm/builder.go`). A CLI too old to fall back that way fails
with its own message, which the engine card shows.

The two LAN access argv are compile-time constants, pinned against `k3sm`
`cmd/k3sm/network.go`; nothing decoded from the status reaches them.

The lifecycle script's own refusals exit 100 (an unsafe path) and 101 (the
signature), above the CLI's codes (0 to 3, and 33 to 95 for a partial stop;
`network lan` adds 4, a failed change whose previous setting could not be
restored).

The copy-out holds `/Library/k3sm.staging.lock` (the outer lock) with
`lockf`; `k3sm install` takes `/Library/k3sm.lock` (the inner one) itself and
accepts the held outer lock once its staging-directory checks pass.

## Gaps in the k3sm contract

- `k3sm status -o json` reports a worker's version as its kubelet version,
  `v<kubernetes>+k3sm.<release>`. The app compares only the release after
  `+k3sm.`, never the Kubernetes version. The value is the node's own report
  and is advisory. A missing or unparseable version is unknown and never
  satisfies the minimum, and an absent `workers` field is unknown, not "no
  workers". An empty list means the server found no other nodes.
- A repair passes no `--user` and no role flag. With neither, `install
  --from-staging` is the CLI's in-place shape: the role comes from the daemon
  plist on disk, a worker keeps its plist's `--server` and its node
  credential, and a server's kubeconfig owner is the owner of the admin
  kubeconfig its arguments record names. With `--user` and no daemon plist on
  disk the CLI would make a first server install instead, which on a worker
  whose plist is gone starts a second cluster; without it, that shape is
  refused. The cost: a server whose recorded kubeconfig is gone is refused
  too, and is reinstalled from Terminal with `--user`.
- Repair rewrites the admin kubeconfig of the user the server's arguments
  record names (the owner of the kubeconfig the last install wrote), who may
  not be the user clicking Repair; the confirmation says so. A worker keeps
  its plist's `--server`, its node credential and its other agent arguments,
  but not an explicit `--node-ip`, which the install renders only from its own
  flag (an assertion of the mesh address the control plane assigns anyway).
- With the command untrusted the app runs nothing, so it cannot read the
  installed release before offering Repair: `k3sm version` and the status
  report both need the command to pass its check, and reading the Go build
  information out of an untrusted binary is a parser of untrusted input the
  app does not carry. The CLI refuses an installed binary whose version
  cannot be read or is not a release (`checkStagedVersion`, no
  `--allow-downgrade`); Repair still shows, and its confirmation names that
  refusal with the others the app cannot check first.
- A purge passes `--user` because the root step runs under `env -i` and the
  CLI would otherwise have no account whose kubeconfig to clean. A plain
  uninstall passes no flag.
- `joinTarget` is `host:port`. The app drops the port, because `install
  --agent` takes the host and adds the join port itself. A present but
  malformed `joinTarget` is refused and does not fall back to the plist.

- The CLI has no machine-readable list of the verbs it supports. The app
  decides that `k3sm stop` exists by version: every release after 0.1.7 has
  it. A CLI that reports no version (an unstamped build) is treated as not
  having it.
- `stoppedBy` has no network field. For an automatic stop, the notification
  shows the stop's reason as the network.
- `k3sm stop` counts a server's joined workers itself but prints the count
  only as text. The app's Stop warning reads the `workers` list of a live
  `k3sm status -o json` instead, and warns when that list is absent.

- The `update` row says `rolling` while a managed update is in progress, but
  the server refreshes it only every 30 seconds and drops it after five
  minutes without a refresh. The app also knows of a roll from its own
  apply, and follows it with `k3sm update status -o json`, which it reads
  while it follows one, and while idle when the row says one is rolling or,
  with the window open, when an update is offered (and once each time the
  menu opens with either).
- The `update` row is recomputed only at the next check, so it can still name
  a release a roll has just installed. The app does not offer that release
  again after it has seen the roll succeed.
- Whether the cluster serves the MLX API is not in any report. The Models
  tab asks discovery (`kubectl api-resources`) after a failed list, rather
  than reading kubectl's error text, which the app does not capture.

- `network.applied` is present only when the caller can read it (root). The
  app runs the status as the user, so k3sm sets `appliedReadable: false` and
  the app says that an administrator can see what is served with `sudo k3sm
  network lan status`. A mismatch between the recorded and the applied setting,
  or a refused change, shows only when the report is readable.
